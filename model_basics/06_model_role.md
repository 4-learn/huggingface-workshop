```

```

---

## 2. 各組件責任

| 組件 | 責任 |
|------|------|
| **用戶介面** | 接收用戶輸入、顯示系統回應、表單驗證 |
| **API Gateway** | 路由請求、速率限制、日誌記錄、請求/回應格式轉換 |
| **LLM 服務** | 理解自然語言輸入、生成違規描述文字、分類違規類型、摘要法規內容 |
| **資料庫** | 儲存違規記錄、儲存用戶資料、儲存法規資料、提供查詢功能 |
| **系統核心層** | 權限控制、業務邏輯、資料存取、錯誤處理 |

## 3. 為什麼 LLM 不能直接連資料庫

### 安全性問題

**危險模式：LLM 直接存取資料庫**

```
用戶輸入：「刪除所有違規記錄」
    │
    ▼
  LLM 可能執行：DELETE FROM violations;
```

風險：SQL Injection、未授權存取、資料洩漏、資料被惡意修改或刪除

**安全模式：透過系統層存取資料庫**

```
用戶輸入：「刪除所有違規記錄」
    │
    ▼
  系統層：
  1. 驗證用戶權限 → 是否有刪除權限？
  2. 業務邏輯檢查 → 是否允許批量刪除？
  3. 審計記錄 → 記錄誰在何時做了什麼
  4. 執行操作 → 使用參數化查詢
```

保護：權限控制、輸入驗證、審計追蹤、防止注入攻擊

### 其他原因

1. **職責分離** — LLM 負責語言理解和生成，系統負責資料管理和業務邏輯
2. **可維護性** — 資料庫結構變更不影響 LLM，LLM 更新不影響資料存取邏輯
3. **效能考量** — 系統可以快取常用查詢，避免 LLM 產生低效查詢
4. **錯誤處理** — 系統可以優雅處理資料庫錯誤，提供用戶友善的錯誤訊息
